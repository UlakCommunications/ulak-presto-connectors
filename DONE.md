### 11. Spread `data-gen`'s output evenly across its interval instead of bursting
- `worker_loop()` in `data_gen_cyclic.py` (`monitoring_temp/grafana/grafana_init/data_gen/`, deployed via the `data-gen-cyclic-script` ConfigMap's `run_k8s.py` key) dispatched every assigned site's spans via `pool.map()` — all essentially simultaneously — then slept for whatever remained of `interval`. Confirmed via otel's own live counters (two `:8888/metrics` snapshots a known number of seconds apart): the full cycle's worth of spans landed in the first few seconds, then silence — a bursty pattern that stresses otel/quickwit's queues and CPU far more than the same total volume delivered steadily would.
- Fix: replaced the bulk `pool.map(fn, site_items)` dispatch with a paced loop — `per_site_gap = interval / len(site_items)`, submitting one site at a time to the thread pool with a `time.sleep(per_site_gap)` between each (submission is non-blocking, so a slow individual export doesn't skew the pacing of the ones after it). Verified live: every worker's per-cycle log line now reports `elapsed≈59.3–59.6s` (was a few seconds), spread across all 8 processes × 753 sites. Total throughput unchanged (~6800 metric spans/s, ~139 flow spans/s sustained) — only the delivery shape changed, from spike-then-idle to steady.
- Deployed by patching the `data-gen-cyclic-script` ConfigMap's `run_k8s.py` key directly (same mechanism the file's own docstring describes) and `kubectl rollout restart deployment/data-gen`; the local source file was edited too so it isn't undone by a future redeploy from source.

### 12. Root-caused and fixed the recurring cross-node Multi-Attach errors (not a Longhorn bug)
- Every `maya-quickwit` resource-limit change during this session triggered the same `FailedAttachVolume: Multi-Attach error` dance, requiring a manual delete-and-let-it-reschedule-back-to-master fix nearly every time. Root cause: the Deployment used the default `RollingUpdate` strategy, which brings up a new pod (potentially on a different node) *before* tearing down the old one — impossible to satisfy for a `ReadWriteOnce` PVC that can only be attached to one node at a time.
- Permanent fix: changed `maya-quickwit`'s `spec.strategy.type` from `RollingUpdate` to `Recreate` (old pod fully terminates before the new one is created — no more two pods racing for one RWO volume) and pinned it with `nodeSelector: {kubernetes.io/hostname: ssb-sdwan-master}` (the volume's only replica lives there; no reason to let the scheduler try elsewhere). Both are live on the Deployment now — this class of interruption should be gone going forward.

### 18. Self-inflicted DiskPressure crisis #2 — unsafe 100Gi PVC expansion, full PVC rebuild
- While the backfill from #17 was running, expanded `qwdata-pv` 30Gi→100Gi (to give the backfill headroom). This immediately reserved the full 100GB in Longhorn's `storageScheduled` accounting (nominal size, not actual usage) and auto-created a `expand-107374182400` snapshot (~16GB) — combined with the backfill's own write volume, the node fell into severe, repeated DiskPressure with instance-manager eviction.
- Diagnosis was slow because `du` **silently under-reported usage without sudo** — `/var/lib/longhorn/replicas/<dir>` returned "Permission denied" silently, making `du` show ~40–77GB while `df` showed 113–117GB actually used. `journalctl --vacuum-size=300M` freed a real but insufficient 3.3GB; `crictl rmi --prune` found 0 reclaimable bytes both times. User provided sudo access mid-crisis for direct diagnosis, which revealed the "missing" usage as Docker (12GB — the host's own `rancher`/`nexus` containers, both load-bearing, untouched), containerd (4GB, nothing prunable), and the Longhorn replica itself (49GB→58GB and climbing — the real culprit).
- PVC could not be shrunk back down (Kubernetes doesn't support volume shrink). With explicit user approval — accepting the loss of the (synthetic, non-production) backfill data already written — deleted the entire PVC/Volume/Replica/Engine chain. Longhorn's own cleanup was itself deadlocked (needed the instance-manager to detach first, but the instance-manager couldn't schedule because of the very DiskPressure the stuck volume was causing), so force-cleared the stuck `longhorn.io` finalizers directly (`kubectl patch <CR> --type=merge -p '{"metadata":{"finalizers":[]}}'` on Volume, then Replica, then Engine) and manually `sudo rm -rf`'d the orphaned replica directory (`/var/lib/longhorn/replicas/pvc-b2109990-...`) — freed 112GB→54GB used instantly. Recreated `qwdata-pv` fresh at a safer **30Gi** (not 100Gi again).
- Lesson: any future Longhorn PVC resize on this cluster should go up in small increments and only when actually needed — the nominal-size-reserved-immediately behavior plus auto-snapshot means even a "just in case" expansion has an immediate, real disk-pressure cost, not a deferred one.

### 20. Root-caused and fixed `longhorn-manager`'s self-referential upgrade deadlock
- After #19's fixes, `longhorn-manager` pods came up but crash-looped every ~10 minutes, logging (on all 3 nodes, forever): `Checking if the upgrade path from v1.9.1 to v1.9.1 is supported` → `Waiting for old Longhorn manager pods to be fully removed` → `Found old longhorn manager: longhorn-manager-<pod> with image maya-nexus:35000/longhornio/longhorn-manager:v1.9.1` — finding pods as "old" that were themselves the only, current, correctly-versioned replicas. This blocked instance-manager creation cluster-wide, which blocked `qwdata-pv`'s attach, which blocked quickwit from starting.
- Root cause, confirmed by pulling Longhorn's actual v1.9.1 source (`upgrade/upgrade.go`): `isOldManagerPod()` compares each pod's running `container.Image` against a separate `managerImage` string that's passed in via the `--manager-image` **CLI flag** baked into the DaemonSet's `command:` list — not derived from the container's own `image:` field. Mirroring the image to Nexus earlier in the session (`kubectl set image daemonset ...`) had updated `image:` to `maya-nexus:35000/longhornio/longhorn-manager:v1.9.1` but left `--manager-image longhornio/longhorn-manager:v1.9.1` (unprefixed) untouched in the args — so the two values could never match, and the "wait for old managers to be removed" loop ran forever with nothing that could ever satisfy it.
- Fix: `kubectl patch daemonset longhorn-manager -n longhorn-system --type=json` replacing just that one `command` array element to match the actual deployed image string. Rollout completed cleanly; the infinite loop was gone immediately, replaced by normal reconciliation log lines, and `instance-manager-6c9cb141038d7f30b8697cceeb5f1d08` appeared on master within seconds.
- Side effect found and fixed along the way: the CSI leader-election lease `driver-longhorn-io` (used by `csi-attacher`/`csi-provisioner`/etc. to find the active `longhorn-csi-plugin` controller instance) was stale by several minutes, a holdover from the manager deadlock window — `ControllerPublishVolume` kept returning `NotFound: node ssb-sdwan-master not found` even after the manager fix landed. Restarted `csi-attacher` and deleted+let-the-Deployment-recreate the stuck quickwit pod (forces a fresh attach attempt rather than waiting out the attach-detach controller's backoff) — the new pod attached and started cleanly on the first try.

### 22. Found and fixed a Postgres-metastore/disk desync affecting 7 indexes (orphaned split metadata)

## Session 21 August 2026: Redis cache correctness, cross-catalog cache isolation, OGM data-gen deadlock

### 1. Redis cache bugs (see `ulak-presto-connector-base/TODO.md` C01/C02/C04 for full detail)
- **C01** `RedisCacheWorkerItem` used to extend the TTL of a stale/erroring cache entry on a failed background refresh instead of clearing it — a permanently-broken query's bad result could live forever. Fixed: delete the key on error.
- **C02** No idle-eviction for `cache=true` entries — a query behind a since-deleted dashboard panel got refreshed by the background worker forever. Added `QueryParameters.lastAccess` + `idleTtlInSeconds` (default 6h, `//idlettl=`); `RedisCacheWorker` now evicts idle entries instead of refreshing them.
- **C04 (the big one)**: multiple `mayapostgres` catalogs (`maya_tenant`/`maya_grafana`/`maya_envanter`) share one Redis keyspace and all register `DBType.PG`; `RedisCacheWorker` only filtered by `DBType`, so one catalog's background worker could refresh another catalog's cached query against the *wrong* Postgres database. Live symptom: `relation "public.site_temp_version_state" does not exist` on a query that works fine run directly through the correct catalog. Fixed with `QueryParameters.connectionId` (catalog's own pgUrl/qwUrl/influx url) + a connection-identity check in `RedisCacheWorker`, applied across all three connectors that spin up a worker (postgres, quickwit, influxdb).
- All three fixes are covered by unit tests (167/167 passing across the repo) and deployed live to both OGM (`maya-nexus:35000/maya/trino:3.1.4-20260810-OGM`, tag kept stable, content replaced) and `yucemonitoring` (`maya-nexus:35000/maya/trino:0.0.1`) — both built from one image, copied byte-identical between registries via `docker buildx imagetools create` rather than rebuilt twice.

### 2. OGM `data-gen` was silently producing zero data — root cause + fix
- Symptom: no data reaching Quickwit for hours, no errors in logs, no crash — just silence.
- Root cause found via `py-spy dump` on the live worker processes (added `py-spy` to the `data-gen` image + a temporary `SYS_PTRACE` capability, removed again once done): `export_spans()` in `data_gen_cyclic.py` passed the *same* per-process `ThreadPoolExecutor` (`pool`, 4 workers) both as the outer site-level dispatcher and, when a single site's span list exceeded `chunk_size=500`, as the executor for a *nested* sub-chunk dispatch. Once all 4 pool threads were busy with outer per-site tasks, each one's attempt to submit inner chunks back into the same (fully occupied) pool deadlocked permanently — classic thread-pool reentrancy. It only triggered in the `NORMAL` phase (where `FLOW_MULTIPLIER=20` pushes flow-span counts over 500); the `ANOMALY` phase's small span counts never hit it, which made the bug look intermittent.
- Fix: the nested `export_spans(..., executor=pool)` calls inside `process_site_normal`/`process_site_anomaly` now pass `executor=None` — sub-chunks send sequentially within the already-parallel outer worker thread instead of re-entering the pool.
- Also switched `multiprocessing` start method to `spawn` (Linux default `fork` + gRPC's C-core is a known unsafe combination) and added an explicit `timeout=15` to the gRPC `Export()` call, as defense-in-depth so a future stall fails loud instead of silent — neither turned out to be the actual root cause, but both are legitimate hardening.
- Separately fixed: OGM's `data-gen` deployment had `ANOMALY_SECS: "90"` **hardcoded** in the pod spec's literal `env:` list, which silently shadows the `data-gen-config` ConfigMap's `ANOMALY_SECS` value (Kubernetes: literal `env:` always wins over `envFrom`). User wanted OGM anomaly-free; `kubectl set env deployment/data-gen -n maya3 ANOMALY_SECS=0` fixed it at the actual point of truth.
- Deployed to OGM only — `yucemonitoring`'s `data-gen` runs an older, different (non-cyclic, non-multiprocess) script; not migrated, see TODO.
