### 1. Four connector bugs found live, fixed, tested, deployed to both clusters
All in `ulak-presto-quickwit-connector`, commits `bc478ab` + `5a0683c` on `1h_rollup` (now MR [!35](https://gitlab.ulakhaberlesme.com.tr/maya/presto-influxdb-connector/-/merge_requests/35) → `develop`):

1. **`QwUtil.executeOneQuery()`'s field-rewrite gate silently skipped.** `QwQueryRewriter.rewriteQueryForHistory()` (rewrites raw-schema `span_attributes.tx` → rollup-schema `tx_max`/`tx_min` — confirmed live that rollup docs only ever have `_min/_max/_avg/_sum/_count`-suffixed fields, never a bare `tx`/`rx`) was gated on `historyIndex.equals(qwIndex)`. Before this feature, `qwIndex` could only ever become byte-identical to the caller's `historyIndex`, so the check always held — the new tier-escalation code can set `qwIndex` to a *derived* index, silently breaking the gate and sending raw field names to a rollup index that doesn't have them (every value comes back `null`). Fixed by computing `historyIndexActive` once, at the exact point `select()` decides to point `qwIndex` at any history index, and threading it explicitly into `executeOneQuery()` instead of re-deriving via string equality.
2. **`HistoryTier.build()` didn't enforce threshold ordering.** A coarser tier configured with a lower threshold than a finer one (live example: `history-tiers=60:3600` vs finest `10800`) could starve the finer tier entirely, since `select()` picks the last tier in ascending-minutes order whose threshold is exceeded, regardless of whether thresholds also increase. Fixed: `build()` now clamps each tier's threshold up to at least the previous (finer) tier's, logging when it does.
3. **`QwUtil.arrangeAggregation()` dropped bucket identity, not just the value, when a leaf metric was null.** This function propagates ancestor bucket context (`key`, `doc_count`) into each leaf metric node before `flatten()` runs. The merge was gated on `value != null` — a metric with no matching value (exactly what bug #1 caused) silently lost the row's `key` too, not just its value, so `flatten()` produced only a bare `.../value` column with nothing identifying which bucket it came from. This is why `/6/key`-style column references (used by `replacefromcolumns`, e.g. the "Host Interface" Grafana variable) could never resolve, and it's why bug #1's symptom looked like generalized JFlat fragility rather than a specific rewrite-gate miss. Fixed: the merge is now unconditional for leaf nodes (`buckets == null`) instead of gated on the value.
4. **`history-time-threshold-seconds` now accepts an explicit `minutes:seconds` pair** (same shape as a `history-tiers` entry), so a catalog can state its finest tier's granularity explicitly instead of `HistoryTier.build()` silently assuming 15m. Bare-number config stays 100% backward compatible. **Follow-up bug caught live only on OGM, not yucemonitoring** (pure coincidence — yucemonitoring's chosen pair, `15:10800`, happened to match the system default exactly, masking it): the factory left the classic threshold `null` to suppress `build()`'s hardcoded 15m entry, but `QwUtil.select()`'s own `catalogHistoryTimeThresholdSeconds != null ? ... : DEFAULT_HISTORY_TIME_THRESHOLD_SECONDS` fallback silently resurrected a phantom `15m@10800s` entry from that same `null`, producing a live `tiers=[15m@10800s, 15m@10800s, 60m@86400s]` on OGM once `15:3600` was configured there. Fixed with an explicit sentinel, `HistoryTier.FINEST_TIER_SUPPRESSED = -1L`, which survives a plain `!= null` check unchanged. Added a regression test mirroring the *real* call chain (factory → `select()`'s fallback → `build()`) rather than calling `build()` directly — the original tests for bug #4 all called `build()` directly and stayed green despite the bug, because they never exercised the actual buggy interaction. This is itself a lesson worth repeating: a passing unit test only proves what it actually exercises.

197/197 unit tests passing (44 new/updated). Deployed and live-verified via direct Trino queries + coordinator log inspection on **both** yucemonitoring (image `1h-rollup-20260827-v2`) and OGM (same tag, image reused via `docker pull`+`tag`+`push` — no rebuild needed since the source was identical). ### 1. Diagnosed OGM demo's live Redis-pool-exhaustion problem (root cause found, not fixed)
- User asked "OGM demo'da problem nedir" — read `maya-trino-single-coordinator` logs directly. Found `redis.clients.jedis.exceptions.JedisException: Could not get a resource from the pool` recurring ~245 times/hour, each preceded by a query stalling 30-110s and ending `USER_CANCELED`.
- Root cause chain, confirmed live rather than just read from code: `maya-quickwit` is pinned via node affinity to `ssb-sdwan-master`, which was running ~72% memory (other two nodes ~5-7%) — caught a live pod reschedule mid-investigation where the replacement pod sat `Pending` (`FailedScheduling: Insufficient memory`) for several seconds before landing. During that window Trino→Quickwit calls slow down or fail (`okio.Timeout.throwIfReached`; some `SLOW_QUERY` log lines hit 300s+, vs. a normal 5-20s). `ConnectorBaseUtil.select()` (`ulak-presto-connector-base/.../caching/ConnectorBaseUtil.java:217-275`) holds its `Jedis` resource for the *entire* method body — including the downstream `exec1.apply(...)` call and `inProgressLock` synchronization — not just the cache GET/SET, so a slow Quickwit call ties up a Redis connection for its full duration. `JedisPool` (`maxTotal=1000`, `blockWhenExhausted=true`, unbounded `maxWait`) exhausts under that load; new borrowers block indefinitely until the outer query is cancelled (~30s), which interrupts the waiting `borrowObject()` and surfaces as the `JedisException` above. Redis itself confirmed healthy throughout (`used_memory` 5.4MB, `blocked_clients:0`, `DBSIZE` 24) — this is a coordinator-side connection-holding design issue plus Quickwit's node-pinning, not a Redis problem.

### 2. Implemented and live-tested `qw-rollup-engine`'s first-run backward backfill
- User wanted a new task's very first run to backfill history (from today back to the source's real earliest data) in addition to the existing forward-only tracking, with forward always taking priority.
- **Design** (full plan in the session transcript, `harmonic-napping-pillow.md`): a second checkpoint (`checkpoint_{name}_backfill`, same `get_last_checkpoint`/`save_checkpoint` functions, no changes to `checkpoint.rs` itself) interpreted as a 4-state sentinel (`-1`=done, `-2`=pending-retry, `0`=untouched, `>0`=in-progress cursor). Backfill can only ever be triggered the one moment both the forward and backfill checkpoints are still `0` — a task with a pre-existing (non-zero) forward checkpoint can structurally never reach that branch, which is what keeps every already-running OGM/yucemonitoring task untouched. A first draft of this gated the check inside `if forward_checkpoint == 0` alone, which a design-review pass caught as buggy: forward's checkpoint goes non-zero within minutes of startup (its first window succeeding), so a process restart mid-backfill would silently and permanently stall it — fixed by making the backfill checkpoint its own source of truth on every restart instead.
- **Implementation** (`qw-rollup-engine`, not yet built/deployed — see TODO.md): `types.rs` gained `source_timestamp_field: Option<String>` (explicit override for the earliest-timestamp probe field, auto-derived from `query_template.aggs.<date_histogram>.date_histogram.field` when unset — covers all 15 real tasks without needing it set). `engine/quickwit.rs` gained `find_earliest_timestamp()` (a single top-level Quickwit `min` aggregation, `max_hits:0` — cheaper than the `timestamp_min`/`timestamp_max` leaf aggregations every task already runs on every window) plus small refactors (`search_url`, `json_num_to_i64`, `normalize_to_nanos`) extracted from existing inline logic in `execute_rollup_single`, now shared. `task_loop.rs` gained the startup decision-table logic and a backfill step in the main loop, inserted only after the existing forward `while` loop fully drains for that pass, advancing at most one window per pass — this is what structurally guarantees forward is never starved (a burst of several backfill windows in a row was explicitly rejected as a design option).
- **Live-tested against the real OGM Quickwit cluster** (`10.20.4.31:30994`), not just unit-reasoned: built the real binary (`~/.cargo-target/debug/qw-rollup-engine` — this machine's shared `target-dir`, see CLAUDE.md gotcha), ran it against an isolated copy of the real `memory_15m` task definition (renamed, separate checkpoint dir, production `tasks.json`/checkpoints untouched). Confirmed: (1) forward drains first, backfill only starts once it's caught up, and proceeds backward in correct 15-min steps; (2) killing the process mid-backfill and restarting resumed correctly from the saved cursor (the exact bug class the design fix above targeted); (3) running with a pre-populated (simulated-production) forward checkpoint never created a backfill checkpoint file at all — the safety guarantee held under a real run, not just by code inspection.
- **Found and fixed a real bug during live testing**: the discovery query used `"0"` as the range lower bound (`span_start_timestamp_nanos:[0 TO ...]`), which Quickwit actually rejects (`invalid query: expected DateTime boundary`) — confirmed via direct `curl` against the live cluster before touching the Rust code. Fixed to `"*"` (open-ended lower bound), re-verified working. Also discovered live that Quickwit returns the aggregation's `value` in scientific notation (e.g. `1.786407173068e18`) rather than a plain integer — the existing `f64`-fallback parsing (reused from `execute_rollup_single`'s already-battle-tested bucket-key handling) already covered this correctly, no additional fix needed.
- `README.md` updated to document the new behavior and the new task field (was previously wrong: claimed "first run never touches history").
- Also corrected a wrong claim made mid-session (via a delegated Explore agent) that `qw-rollup-engine`'s Trino engine path was "never used" — user pushed back, `git log --all --grep=trino` showed it was actually used in production for about a day (`57a1d03` fix, then `34f1cc4` revert the next day) before being abandoned in favor of Quickwit. ### 11. Spread `data-gen`'s output evenly across its interval instead of bursting
- `worker_loop()` in `data_gen_cyclic.py` (`monitoring_temp/grafana/grafana_init/data_gen/`, deployed via the `data-gen-cyclic-script` ConfigMap's `run_k8s.py` key) dispatched every assigned site's spans via `pool.map()` — all essentially simultaneously — then slept for whatever remained of `interval`. Confirmed via otel's own live counters (two `:8888/metrics` snapshots a known number of seconds apart): the full cycle's worth of spans landed in the first few seconds, then silence — a bursty pattern that stresses otel/quickwit's queues and CPU far more than the same total volume delivered steadily would.
- Fix: replaced the bulk `pool.map(fn, site_items)` dispatch with a paced loop — `per_site_gap = interval / len(site_items)`, submitting one site at a time to the thread pool with a `time.sleep(per_site_gap)` between each (submission is non-blocking, so a slow individual export doesn't skew the pacing of the ones after it). Verified live: every worker's per-cycle log line now reports `elapsed≈59.3–59.6s` (was a few seconds), spread across all 8 processes × 753 sites. Total throughput unchanged (~6800 metric spans/s, ~139 flow spans/s sustained) — only the delivery shape changed, from spike-then-idle to steady.
- Deployed by patching the `data-gen-cyclic-script` ConfigMap's `run_k8s.py` key directly (same mechanism the file's own docstring describes) and `kubectl rollout restart deployment/data-gen`; the local source file was edited too so it isn't undone by a future redeploy from source.

### 12. Root-caused and fixed the recurring cross-node Multi-Attach errors (not a Longhorn bug)
- Every `maya-quickwit` resource-limit change during this session triggered the same `FailedAttachVolume: Multi-Attach error` dance, requiring a manual delete-and-let-it-reschedule-back-to-master fix nearly every time. Root cause: the Deployment used the default `RollingUpdate` strategy, which brings up a new pod (potentially on a different node) *before* tearing down the old one — impossible to satisfy for a `ReadWriteOnce` PVC that can only be attached to one node at a time.

### 18. Self-inflicted DiskPressure crisis #2 — unsafe 100Gi PVC expansion, full PVC rebuild
- While the backfill from #17 was running, expanded `qwdata-pv` 30Gi→100Gi (to give the backfill headroom). ### 20. Root-caused and fixed `longhorn-manager`'s self-referential upgrade deadlock
- After #19's fixes, `longhorn-manager` pods came up but crash-looped every ~10 minutes, logging (on all 3 nodes, forever): `Checking if the upgrade path from v1.9.1 to v1.9.1 is supported` → `Waiting for old Longhorn manager pods to be fully removed` → `Found old longhorn manager: longhorn-manager-<pod> with image maya-nexus:35000/longhornio/longhorn-manager:v1.9.1` — finding pods as "old" that were themselves the only, current, correctly-versioned replicas. ### 2. OGM `data-gen` was silently producing zero data — root cause + fix
- Symptom: no data reaching Quickwit for hours, no errors in logs, no crash — just silence.
- Root cause found via `py-spy dump` on the live worker processes (added `py-spy` to the `data-gen` image + a temporary `SYS_PTRACE` capability, removed again once done): `export_spans()` in `data_gen_cyclic.py` passed the *same* per-process `ThreadPoolExecutor` (`pool`, 4 workers) both as the outer site-level dispatcher and, when a single site's span list exceeded `chunk_size=500`, as the executor for a *nested* sub-chunk dispatch. Once all 4 pool threads were busy with outer per-site tasks, each one's attempt to submit inner chunks back into the same (fully occupied) pool deadlocked permanently — classic thread-pool reentrancy. It only triggered in the `NORMAL` phase (where `FLOW_MULTIPLIER=20` pushes flow-span counts over 500); the `ANOMALY` phase's small span counts never hit it, which made the bug look intermittent.
- Fix: the nested `export_spans(..., executor=pool)` calls inside `process_site_normal`/`process_site_anomaly` now pass `executor=None` — sub-chunks send sequentially within the already-parallel outer worker thread instead of re-entering the pool.
- Also switched `multiprocessing` start method to `spawn` (Linux default `fork` + gRPC's C-core is a known unsafe combination) and added an explicit `timeout=15` to the gRPC `Export()` call, as defense-in-depth so a future stall fails loud instead of silent — neither turned out to be the actual root cause, but both are legitimate hardening.
- Separately fixed: OGM's `data-gen` deployment had `ANOMALY_SECS: "90"` **hardcoded** in the pod spec's literal `env:` list, which silently shadows the `data-gen-config` ConfigMap's `ANOMALY_SECS` value (Kubernetes: literal `env:` always wins over `envFrom`). User wanted OGM anomaly-free; `kubectl set env deployment/data-gen -n maya3 ANOMALY_SECS=0` fixed it at the actual point of truth.
- Deployed to OGM only — `yucemonitoring`'s `data-gen` runs an older, different (non-cyclic, non-multiprocess) script; not migrated, see TODO.
