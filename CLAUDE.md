## Architecture & Configuration
- **Multi-tier history routing:** `history-time-threshold-seconds` (also takes an explicit `minutes:seconds` pair) + `history-tiers` (CSV `minutes:thresholdSeconds`) in `quickwit.properties` pick the coarsest rollup index a query's range clears (`HistoryTier`/`HistoryIndexResolver`) — check the live ConfigMap, not this doc. `QwQueryRewriter.java` rewrites raw field names (`tx`) to rollup ones (`tx_max`) whenever `qwIndex` points at a history index, gated on `QwUtil`'s explicit `historyIndexActive` flag, not `historyIndex.equals(qwIndex)`.
- **Custom JSON flattener** (`QwUtil.flattenJsonNode`/`arrangeAggregation`) parses Quickwit responses; verify any fix by running it through Trino live (`kubectl cp` a `.sql` into the trino-coordinator pod, `trino -f`; `trino --execute "$(cat file)"` doesn't survive multi-KB SQL with embedded quotes). `arrangeAggregation()` only propagates a bucket's `key` into its leaf metric when that leaf's value is non-null. Grafana's trino-datasource plugin **base32-encodes** passthrough query bodies — decode `system.runtime.queries.query` (`base64.b32decode`) to see the real query, don't hand-reconstruct from the dashboard JSON.
- **Redis:** `QueryParameters.connectionId` scopes `RedisCacheWorker` per catalog — see [`ulak-presto-connector-base/CLAUDE.md`](ulak-presto-connector-base/CLAUDE.md). `ConnectorBaseUtil.select()` holding its Jedis connection across the whole downstream fetch (not just cache GET/SET) is the pool-exhaustion root cause — fix priority undecided, see TOBEDECIDED.md.
- **Image registries:** OGM/yucemonitoring's `maya-nexus:35000/...` are different physical registries — push each explicitly, `kubectl set image` by hostname not IP. OGM's `maya-nexus` → `ssb-sdwan-worker1`/192.168.109.204 (`/etc/hosts` on all 3 OGM nodes is the source of truth if it moves again). **No OGM node has real internet or a mirror for bare `docker.io`/`registry.k8s.io`/etc. images** — mirror in via `skopeo copy --dest-tls-verify=false --dest-creds admin:nexus2025! docker://<source> docker://192.168.109.204:35000/<repo>:<tag>` from **outside** the OGM network (e.g. Claude's own session).
- **Quickwit:** metastore is Postgres-backed, independent of `qwdata` — clear orphaned splits via `PUT /api/v1/indexes/{id}/clear`, but the **physical disk isn't reclaimed until the GC sidecar actually runs** (a `clear()` that doesn't move `df` usage isn't evidence the volume is too small — check GC health first). Rejects `"0"` as a datetime lower bound (use `"*"`). Hard-caps `max_hits`/`start_offset` at 10,000. `aggregation_bucket_limit` (`SearcherConfig`, default 65000) is **baked into OGM's `maya-quickwit` image**, not a ConfigMap — no `/quickwit/config` volume mount exists, so raising it needs an image rebuild (confirmed 2026-09-01, see TOBEDECIDED.md).
- **`../qw-rollup-engine`** populates the rollup indexes this connector reads; Helm chart in **`helm_repo1`** (sibling of `ng_sdn` under `maya3/`, not `ai/anomaly` — see DONE.md). `tasks.json`/`config.json` are ConfigMap-mounted (`qw-rollup-engine-config`), read once at startup — **the live ConfigMap, the chart's bundled copy, and the repo's own committed files can all disagree; diff live against repo `master` before trusting any of them** (OGM's live ConfigMap still has `intervals:[15,60]` though `master`'s `ca6f931` removed 60m for OOM safety weeks ago — undeployed, see TODO.md). `max_concurrent_tasks`/`window_pacing_ms`/`idle_sleep_secs` bound every in-flight query, including per-partition sub-queries. Checkpoint backend (`checkpoint_type: "redis"|"file"`) resolves once at startup, no runtime fallback (2026-09-02/03 rework, built+pushed, not deployed — see DONE.md); `"file"` mode needs `podSecurityContext.fsGroup`=10001. Backward backfill (`c99300c`) is **permanently inert for any task whose forward checkpoint predates it** — check a `dest_index`'s Quickwit `/describe` for real coverage, not `tasks.json`. A separate, undocumented **"prod"** environment also runs this engine — ask, don't guess. "OGM demo" = "OGM prod" (`192.168.109.203`/`maya3`), same target.
- **OGM's `ssb-sdwan-master` (192.168.109.203) has repeatedly gone fully unresponsive** under heavy concurrent I/O — root-cause investigation lives in `machine_ops`, not here.
